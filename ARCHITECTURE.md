# Architecture

## Current boundary

Koshara is one Next.js App Router application under `apps/web`. It is a client-side hackathon demo: Next.js serves the interface and static assets, while React state and browser local storage provide persistence.

The root pnpm workspace exists for shared commands and future growth. There are currently no `packages/*` workspaces, backend services, server actions, route handlers, authentication providers, databases, or cloud storage adapters.

## Application shape

The public landing page is `/`. The application shell contains five local routes:

- `/dashboard`: balances, cash flow, recent activity, and spending attention.
- `/transactions`: searchable and editable transaction ledger.
- `/statements`: AI-assisted staging and human review of proposed statement rows.
- `/accounts`: local financial account management.
- `/categories`: category budgets and spending analytics.

`KosharaRuntime` hydrates the local store and registers the page-specific WebMCP tools. The shell, pages, dialogs, tables, and forms use Astryx components; Recharts renders dashboard charts.

## State and persistence

`apps/web/src/lib/koshara-store.ts` is the state boundary. It:

- starts with synthetic data generated by `koshara-seed.ts`;
- hydrates once from the `koshara.finance.v1` local-storage key;
- validates mutations before committing them;
- updates account balances when transactions change;
- persists accounts, categories, transactions, and statement-review sessions in one browser-local snapshot;
- exposes a reset path back to the synthetic seed.

Currency values are represented as integer minor units in application state. External tool results convert them to INR decimal amounts at the boundary.

This storage is intentionally single-browser and single-user. Clearing site data removes local changes. There is no synchronization, account recovery, tenancy, or remote backup.

## WebMCP boundary

`apps/web/src/lib/webmcp-tool-registry.ts` is the tool contract. Tools are grouped around accounts, categories, transactions, spending insights, and statement review. Read-only annotations distinguish inspection from mutation.

The tool layer validates required fields, enums, dates, positive amounts, references, confidence values, and duplicate candidates before calling the store. Statement import is deliberately staged: an agent proposes rows and groups, while the person reviews and approves them in the UI.

Koshara does not upload a statement or call an AI model itself. A compatible external agent reads the statement under that agent's own data policy, then calls Koshara's structured tools.

## Deliberately deferred

Clerk authentication, Supabase/PostgreSQL, household sharing, Gmail access, server-side file upload/parsing, cloud document storage, cross-device sync, and production observability are future features. They should be reintroduced only with a new documented architecture and security review; no dormant scaffolding for them remains in the demo.
